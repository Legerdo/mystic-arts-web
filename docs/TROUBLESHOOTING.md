# 웹 포팅 트러블슈팅

현재 배포는 **원본 x86 게임 + Unicorn.js WASM + Phaser**입니다. BoxedWine/Wine은 초기 호환성·성능을 확인한 이전 경로입니다. 과거 엔진 문제와 현재 상태를 구분합니다.

## 실행 중 먼저 확인할 사항

| 증상 | 확인 / 대응 |
|---|---|
| 예전 UI나 12FPS 버전이 열린다 | [공개 Pages](https://legerdo.github.io/mystic-arts-web/) 또는 `npm run preview`로 실행합니다. 로컬 최상위 `dist/`는 Wine 기준선입니다. 새로고침 후 `build-manifest.json`을 확인합니다. |
| HTML을 직접 열었더니 Worker 오류 / 검은 화면 | `file://` 대신 정적 HTTP(S)를 사용합니다. 서버 루트는 `phaser/native-core/dist/`입니다. |
| 첫 화면에서 소리가 나지 않는다 | 브라우저 음향 잠금은 `게임 실행` 클릭으로 해제합니다. 음소거 체크와 탭 음소거를 확인합니다. MIDI 음색은 Windows와 다를 수 있습니다. |
| 기술이 발동하지 않는다 | 앞/뒤는 바라보는 방향입니다. `+`는 동시, `후`는 순서 입력입니다. 같은 방향은 중간에 떼고 빠르게 다시 누릅니다. 지상/공중·기력·회복·명중 직후 연결 조건을 확인합니다. |
| UI 조작 후 방향키가 먹지 않는다 | 게임 영역을 클릭합니다. 버튼·링크에 입력 중에는 게임 키를 보내지 않습니다. 확대·전체화면·포커스 상실 때 눌린 키를 해제합니다. |
| 전체화면에서 기술표가 사라진다 | 의도한 동작입니다. 게임만 표시하며 Esc로 안내 화면에 복귀합니다. |
| 작은 화면에서 안내 일부만 보인다 | 패널의 `‹` / `›`로 다음 항목을 읽습니다. 선택 탭과 세로 스크롤은 없습니다. |
| EXIT 후 게임 화면이 사라진다 | Worker·음향·Phaser 세션을 정리한 정상 종료입니다. `게임 실행`으로 다시 시작합니다. |
| 현재 위치가 저장되지 않는다 | 원본은 20바이트 클리어/해금 기록입니다. 중간 위치와 옵션 전체 저장은 아닙니다. |
| localhost 기록이 Pages에 없다 | 저장은 사이트 주소·브라우저별로 구분됩니다. 다른 주소의 저장 영역을 같은 기록으로 취급하지 않습니다. |
| 타격·사망·전환 순간 화면이 멈춘다 | 원본 hit-stop/slow 연출과 실제 처리량 문제를 구분해야 합니다. 콤보 벽 충돌 장면 전체의 대조는 아직 완료되지 않았습니다. |

## 1. 실행은 되지만 약 12FPS였던 Wine 경로

BoxedWine Web은 WASM x86 인터프리터로 원본과 Wine을 함께 실행했습니다. 프로파일의 병목은 GPU 업로드보다 `NormalCPU` 디스패치와 `KMemory::readd/writed`의 MMU 접근이었습니다. Canvas `putImageData` 평균은 약 0.033ms였습니다.

tail-call, Binaryen 최적화와 팔레트·copy·alpha·mix·filter 5루프 sidecar 가속으로 약 43~48FPS까지 올렸지만 1초 안팎 정지와 입력 꼬리 지연이 남았습니다. 286초/30구간 평균 46.21FPS만으로 안정적인 30FPS라고 판정하지 않았습니다.

최종적으로 Windows/Wine 전체 대신 원본 게임 코드와 필요한 플랫폼 경계를 직접 실행하는 현재 엔진을 구현했습니다. 게임 시간을 늦추거나 새 AI·전투로 대체하지 않았습니다.

근거: [Wine 재개 기록](PERFORMANCE-RESUME-20261018.md), [런타임 감사](PERFORMANCE-RUNTIME-AUDIT.md), [게스트 CPU 분석](PERFORMANCE-GUEST-CPU.md).

## 2. Wine 레지스트리 저장이 정지의 원인이었나?

약 30초 시점 정지에서 wineserver/libc/libX11 샘플을 찾았습니다. ELF/PE 1,112개를 대조해 10개 주소에서 96바이트 서명이 일치했고 IDA에서 레지스트리 문자열·헤더 직렬화 경로를 확인했습니다. Wine 6.0 [server/registry.c](https://github.com/wine-mirror/wine/blob/wine-6.0/server/registry.c)도 dirty branch를 주기적으로 저장합니다.

**유력한 원인이라는 증거이며 통제된 인과성 A/B가 완료된 것은 아닙니다.** 모든 정지가 레지스트리 때문이라고 확정하지 않습니다. 자동저장을 끄거나 주기를 늘려 문제를 숨기지 않았습니다.

현재 엔진은 Wine 레지스트리를 실행하지 않습니다. 게임의 원본 저장 함수와 20바이트 형식을 유지해 브라우저 저장에 연결합니다. Wine 저장 자체의 의미 보존 가속을 완료한 것과는 다릅니다.

## 3. 가속 코드의 속도보다 동등성이 먼저

| 문제 | 수정 / 현재 판정 |
|---|---|
| 초기 CPU 샘플 구조 오프셋 오류 | 교정한 구조로 재분석했습니다. 잘못된 샘플은 hotspot 증거로 사용하지 않습니다. |
| 초기 Wine 루프의 차등 실패 후 부분 상태로 실행 | v2에서 복원/중단 처리를 수정했습니다. 과거 v1 결함을 현 버전 미수정 결함으로 기재하지 않습니다. |
| 루프가 scheduler quantum을 넘음 | 반복 수·실행량·quota/yield 경계 사례를 검사했습니다. |
| 물리 주소 + 길이의 i32 wrap | 넓은 정수 검사로 OOB trap 재현 입력을 거부합니다. 정상 게임에서 발생한 주소라는 뜻은 아닙니다. |
| 생성 소스와 과거 WAT/WASM 불일치 | 기존 후보를 보존하고 입력·컴파일러·출력 해시를 고정한 별도 후보로 검증했습니다. |
| 현재 엔진 사각형 경계의 포함 비교 오류 | 원본 CPU의 반환/메모리와 대조해 포함 조건을 수정했습니다. |
| 빈 RET 함수에서 불필요한 진단 명령 생성 | 원본 no-op은 원본 CPU가 그대로 실행하게 했습니다. 진단 출력을 게임 동작으로 취급하지 않습니다. |

현재 차등 검사는 RAM/힙, 반환값, 그리기·음향 명령, 최종 인덱스 픽셀을 비교합니다. 396개 보조 사례와 10,200 fixture 프레임이 대상이며 CPU의 모든 임시 레지스터·예외와 Windows 플랫폼 전체의 증명은 아닙니다.

## 4. Unicorn.js의 메모리 접근 비용

전체 Win32 경로를 제거해도 에뮬레이터 API로 메모리를 자주 읽으면 호출 비용이 큽니다. 기존 WASM 힙 getter와 메모리 뷰를 사용했습니다. CPU/WASM 바이트는 바꾸지 않았고 [생성 소스](../phaser/native-core/prepare.mjs)와 [출처 해시](../phaser/native-core/adapter-provenance.json)를 보존합니다.

실제 프로파일의 충돌·지형·커맨드·dirty 영역 보조 함수 8개만 가속합니다. AI·전투 상태 머신은 원본 x86입니다. instruction-count 모드는 초기화 중 번역기 오류를 일으켜 정상 모드(count=0)를 사용하며 CPU는 종료 가능한 Worker 안에서 실행합니다.

도착한 프레임마다 Phaser를 수동 갱신하는 실험은 약 59FPS대로 악화되어 채택하지 않았습니다. 렌더 호출 증가를 게임 FPS 향상으로 보지 않습니다.

## 5. MIDI와 효과음

초기 Wine/SDL MIDI send는 성공을 반환해도 소리가 나지 않아 원본 WinMM/OSS 이벤트를 TinySynth로 연결했습니다. 현재 엔진은 원본 MIDI 이벤트·루프 플래그와 DirectSound PCM/음성 선택을 Web Audio에 연결합니다.

사용자 클릭 후 음향을 시작하고 MIDI 2번 곡의 일회 재생 등 원본 플래그를 반영합니다. 새 BGM으로 교체하지 않습니다. 음색과 실제 스피커 지연까지 원본과 같다는 뜻은 아닙니다.

## 6. EXIT 오류와 AudioContext 중복

원본 EXIT의 `USER32.dll!DestroyWindow`에서 미지원 import 오류가 났습니다. 창 파괴를 정상 종료 이벤트로 바꾸고 Worker 종료, 눌린 키 해제, PCM/MIDI 정지, AudioContext suspend, Phaser destroy를 수행합니다. 저장은 삭제하지 않습니다.

첫 수정 뒤 AudioContext 중복을 재시작 검사에서 찾았습니다. TinySynth 자체 컨텍스트를 PCM과 공유·재사용하게 수정했습니다. 2회 종료 후 세 번째 시작에서 실제 전투·음향·저장 복원을 확인했습니다. [EXIT 결과](../phaser/native-core/exit-no-tabs-final-02/result.json)를 보존합니다.

## 7. 기술표와 게임만 전체화면

기술표는 인터넷 두 자료와 원본 커맨드/플레이어 분기에 일치한 항목만 표시합니다. 명칭이 엇갈리는 기술에 확정적인 새 이름을 붙이지 않았습니다.

선택 탭을 제거하고 게임 양옆에 배치했습니다. 동작 이름·키캡·조건을 분리하고 `후`/`+`, 기력, 지상 3타 연결을 구분했습니다. 높이가 부족하면 완전한 항목 단위로 페이지를 나눕니다. 작은 화면의 잘린 설명은 짧게 정리하고 폭·줄바꿈을 조정했습니다.

전체 앱을 fullscreen으로 만들면 기술표도 나와 게임 영역만 대상으로 바꿨습니다. Esc는 먼저 전체화면을 해제하며 pause 입력과 충돌하지 않습니다. 화면 전환 때 입력 포커스를 복구합니다.

## 8. 다른 웹 포팅을 바로 가져오지 않은 이유

- Compile/뿌요뿌요의 MAME·EmulatorJS 사례는 주로 아케이드/콘솔 ROM이어서 Win32 EXE의 API를 그대로 해결하지 않습니다.
- 조사 시점 BottleShip은 x86→WASM JIT 후보였지만 MIDI 미지원과 WebGPU/SAB/격리 조건이 남았습니다. 검증된 대체재로 취급하지 않았습니다.
- Wine-Assembly는 실제 브라우저에서도 폰트 열거 대기로 검은 화면이었습니다.
- 현재 방식은 Phaser에 임의 AI·전투를 재구현하는 대신 **원본 코드 + 필요한 Win32 경계**로 범위를 줄인 선택입니다.

조사 당시 고정한 소스/실행의 결과이며 지금 모든 upstream 버전에 같은 제한이 있다는 뜻은 아닙니다. [조사 기록](WEB-EMULATION-RESEARCH-20261018-UPDATE.md)에 출처·버전을 남겼습니다.

## 검증 도구도 관측에 영향을 줄 수 있음

스크린샷 분석 자체가 입력 시점에 영향을 준 사례가 있어 기존 픽셀 판정과 합격 기준을 유지하며 검출 비용을 줄였습니다. Wine ZIP의 이동 후 점프 재실패를 통과로 덮지 않았습니다.

새 결과에는 새 폴더/파일 이름을 사용합니다. 평균 FPS로 긴 정지·누락 입력·동등성 실패를 감추지 않습니다. 재현 명령과 판정은 [VERIFICATION.md](VERIFICATION.md)에 모았습니다.
